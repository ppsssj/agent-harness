# v0.2 Installation Design

**Status:** design only. This document proposes a Windows-first installer; it does not add scripts, change host configuration, create links, or install anything.

**Research access date:** 2026-09-25. Statements below are labeled **FACT**, **INFERENCE**, **ASSUMPTION**, or **DECISION**. A fact is limited to what an official source documents.

## 1. Goal

Enable one user to install the eight reusable agent-harness skills once and use them from unrelated projects on Windows. The harness repository remains an independent source repository. Project `AGENTS.md`, `CLAUDE.md`, `DESIGN.md`, commands, architecture, and product constraints remain in each project; no project records an absolute path to this repository.

The target experience is deliberately limited: update the source repository by the user's normal Git workflow, then run the installer again to synchronize a known snapshot. It does not promise that an installed file alone can force an LLM to select a workflow.

## 2. Current v0.1 architecture

**FACT:** v0.1 is a documentation/workflow system: canonical `AGENTS.md`, a minimal `CLAUDE.md` adapter, eight `skills/*/SKILL.md` procedures, shared `references/`, output `templates/`, source provenance, and lightweight eval guidance. The skills already use Agent Skills-compatible frontmatter (`name`, `description`) and progressive disclosure.

**DECISION:** v0.2 distributes the existing `skills/` folders unchanged, plus their required shared `references/` and `templates/` artifacts. It does not distribute the repository-level `AGENTS.md`, `CLAUDE.md`, docs, evals, or Git metadata as global host instructions. The mapping below preserves current relative links without exposing the whole checkout.

## 5. Evidence and decision register

| Type | Statement | Consequence |
| --- | --- | --- |
| **FACT** | Both hosts natively recognize a user-level skill directory and `SKILL.md` metadata. | A global instruction adapter is not required for basic discovery. |
| **FACT** | Both hosts officially document symbolic-link support for skill folders. | Linking is a supported option, not an implementation necessity. |
| **FACT** | Neither source documents Windows junctions as a host-specific skill-install mechanism. | A junction is not a supported v0.2 mechanism. |
| **FACT** | Both hosts offer native plugin mechanisms. | Plugins are a viable future distribution channel. |
| **INFERENCE** | Copying an owned, verified snapshot is safer than linking a mutable checkout into globally active behavior. | Prefer copy for a first Windows installer. |
| **INFERENCE** | A broad global `AGENTS.md`/`CLAUDE.md` adapter would make project-instruction conflicts more likely than direct skills. | Do not install a global adapter in v0.2. |
| **ASSUMPTION** | The installer will run in the same Windows user context as the target host and can resolve that user's home directory. | Doctor must show the resolved paths and fail safely if the user context is ambiguous. |
| **ASSUMPTION** | The eight current skill folders will be made self-contained as part of implementation planning. | Do not ship until reference/template dependencies are explicitly packaged or resolved. |
| **DECISION** | v0.2's first implementation targets direct user-scope copies, with explicit update and ownership records. | No symlinks, junctions, global instruction edits, or plugin packaging in the first installer PR. |

## 6. Distribution strategy comparison

| Strategy | Official support | Windows / privileges | Update and uninstall | Main risks | v0.2 result |
| --- | --- | --- | --- | --- | --- |
| A. Copy to host user-skill directory | Both hosts document the destination directories. | Normal user write access; no Developer Mode or Administrator expected. | Re-run installer after source update; manifest can remove only owned copies. | Duplicate files can become stale if user forgets update. | **Recommended** |
| B. Symbolic links to source skills | Both hosts document symlinked skill folders. | Windows symlink creation can require Developer Mode or elevation depending on policy. | Source edits immediately affect hosts; uninstall removes links. | Broken links, mutable active behavior, cross-volume and policy failures. | Not default; possible later opt-in. |
| C. Junctions | No host-specific documentation found. They may look like directories to Windows APIs. | Usually user-creatable for directories, but semantics and tooling differ from symlinks. | Similar to links. | Undocumented host behavior, stale targets, difficult diagnosis. | Rejected. |
| D. Native plugin / marketplace | Both hosts document plugins, but their local packaging, marketplace, and installation flows differ. | No link privilege requirement for normal installs. | Host-managed update/uninstall. | Packaging and compatibility work; plugin may expose more than skills; local-marketplace availability varies by surface. | Defer to a later distribution release. |
| E. Minimal global instruction adapter | Both hosts document global instructions. | Plain file copy. | Update/revert one file. | Always-on context, project conflict risk, and indirect skill discovery. | Rejected for v0.2. |

**DECISION:** choose A. It is the smallest cross-host, documented mechanism that does not modify project repositories or expose the source repository at runtime. The update command is intentionally explicit: update the source with Git, review it, then run the installer with update intent. A copy is a versioned installed snapshot, not a live checkout.

## 7. Recommended architecture

Future installation is an ownership-aware synchronizer, not a generic configuration manager:

1. Locate a valid agent-harness source checkout selected by the user.
2. Validate the expected eight skill manifests and the installable dependency layout.
3. Detect Codex and Claude independently.
4. Resolve only each host's documented user-scope skill location in that user's context.
5. Copy only agent-harness-owned skill artifacts, after collision and path-safety checks.
6. Record installed paths, source commit/version, and content hashes in an agent-harness-owned state record outside host configuration.
7. Report actions, skips, conflicts, and next-session requirements.

It must never write `AGENTS.md`, `CLAUDE.md`, `config.toml`, `settings.json`, PATH, project files, or unrelated host skills. An installer should not call `git pull`; source update remains a deliberate user action because it changes globally active behavior.

### Installed artifact mapping

The current source links from `skills/<name>/SKILL.md` to `../../references/` and `../../templates/`. Therefore each host integration root maps these source directories as follows:

| Source artifact | Codex destination beneath `$HOME/.agents` | Claude destination beneath `~/.claude` |
| --- | --- | --- |
| `skills/<name>/` | `skills/<name>/` | `skills/<name>/` |
| `references/` | `references/` | `references/` |
| `templates/` | `templates/` | `templates/` |

**DECISION:** these three destination trees are one agent-harness-owned installation unit. Before copying any tree, the installer must require every existing target to be either absent or manifest-owned with an expected hash. This preserves the existing skill files, avoids copying the whole source checkout, and makes a foreign `references/` or `templates/` directory a safe collision rather than an overwrite opportunity.

## 8. Proposed directory layout

This is a next-PR design, not a request to create these paths now.

```text
agent-harness/
  skills/                         # source workflows
  adapters/
    codex/                         # host packaging/readme material only if needed
    claude/                        # host packaging/readme material only if needed
  scripts/
    install.ps1
    uninstall.ps1
    doctor.ps1
  docs/
    INSTALLATION.md
    V0.2_INSTALLATION_DESIGN.md
```

The installer state belongs under a per-user agent-harness state root (proposed `%USERPROFILE%\.agent-harness\install-state.json`), not in `~/.codex`, `~/.claude`, or any project. Its schema records schema version, source checkout identity, source Git commit if available, host, destination, owned relative paths, installed hashes, and install timestamp. This is a **DECISION** for future implementation, not a documented host path.

## 9. Installer responsibilities

`install.ps1` should:

- support a dry-run default or explicit preview and require an explicit apply action;
- detect the source checkout by script location, validate it, and report the resolved Unicode-safe path;
- detect hosts without assuming that a missing executable means a missing directory, or vice versa;
- resolve Codex's user-skill path from its documented `$HOME/.agents/skills` contract and Claude's from `CLAUDE_CONFIG_DIR` or `%USERPROFILE%\.claude\skills`;
- validate each source `SKILL.md` name/description and the required shared `references/` and `templates/` files;
- preflight every destination: if a target exists but is not in the ownership manifest with the expected hash, stop for that host rather than overwrite it;
- stage and verify copies before replacing an existing harness-owned destination; write the state record only after successful verification;
- be idempotent: an identical owned install is reported as unchanged;
- print host, destination, source revision, skill names, hashes, changed paths, skipped hosts, and failures.

It should treat host detection as `NOT INSTALLED`, not an error, and allow installation for one host while reporting an independent failure for the other.

## 10. Uninstaller responsibilities

`uninstall.ps1` should read the ownership record, recompute installed hashes, and remove only destinations that both match a recorded agent-harness path and match the installed hash. It must preserve a modified or unrecognized destination and report it as manual cleanup required. It removes the per-user state record only when no owned integration remains. Partial, missing, or stale state is a non-destructive failure; it must never delete a whole host skills directory.

## 11. Doctor responsibilities

`doctor.ps1` reports files and discovery prerequisites, not model behavior:

```text
Repository
[PASS/FAIL] source repository found and expected skill manifests present

Codex
[PASS/FAIL/NOT INSTALLED] host detected
[PASS/FAIL] documented user-skill destination resolved
[PASS/FAIL] harness integration hashes and manifests match
[PASS/FAIL] expected eight skills are present

Claude
[PASS/FAIL/NOT INSTALLED] host detected
[PASS/FAIL] documented user-skill destination resolved
[PASS/FAIL] harness integration hashes and manifests match
[PASS/FAIL] expected eight skills are present

Skills
[PASS/FAIL] research, design-research, frontend-design, architecture
[PASS/FAIL] implementation, root-cause, verification, pr

Result: HEALTHY / DEGRADED / BROKEN
```

`HEALTHY` means all selected installed hosts have validated artifacts. `DEGRADED` means no destructive condition but a host is absent, stale, modified, or partially installed. `BROKEN` means an ownership/path/integrity check fails. Doctor cannot prove implicit skill selection, instruction adherence, a host's current process cache, or LLM behavior; it directs users to the smoke tests for those questions.

## 12. Ownership model

| Layer | Owns | Must not own |
| --- | --- | --- |
| Global harness install | The eight installed reusable workflows and its state manifest | Host-wide instructions, project files, user-created skills, host settings |
| Project | Stack, commands, architecture, invariants, repository conventions, `AGENTS.md`, `CLAUDE.md`, `DESIGN.md` | A dependency on this checkout's path |
| Current task | User request, acceptance criteria, immediate constraints | Persistent global or project policy unless intentionally changed |

Name collisions are a safety boundary. If a personal host skill already occupies a canonical harness skill destination and is not manifest-owned, installation must not replace it. The first installer should report the collision and leave selection to the user; silent renaming would change invocation/discovery semantics.

## 13. Update model

1. User updates the independent source repository with their normal reviewed Git process.
2. User runs installer preview, reviews the listed source commit/hash and destination changes, then applies.
3. Installer copies a new verified snapshot only over matching agent-harness-owned artifacts.
4. User starts a new Codex or Claude Code session after an update. Codex documents automatic skill detection but also recommends restart if a change is not visible; Claude behavior is validated with a fresh session.
5. Doctor compares installed hashes and reports stale, modified, or missing artifacts.

No source update is automatic. This makes supply-chain changes reviewable and makes rollback possible by checking out a known source commit and running the installer again.

## 14. Smoke-test plan

Run these after installation validation in a newly created, unrelated temporary Git repository. Do not mention agent-harness, paths, or skill names in the prompt. Run each test in a fresh Codex session and a fresh Claude Code session; preserve transcripts/observations separately from the temp repository.

| Test | Prompt | Expected behavioral evidence |
| --- | --- | --- |
| A: bug | `There is a failing test in this project. Find the cause and fix it.` | Agent investigates/reproduces before editing, follows root-cause -> implementation -> verification, and reports fresh checks. |
| B: visual | `Create a new landing page direction for this product.` | For meaningful visual work, agent establishes reference direction/design research before frontend implementation and performs applicable verification. |
| C: architecture | `We need to add persistent storage. Determine the appropriate architecture before implementing it.` | Agent researches/compares options and records a decision before implementation. |

Installation validation and behavioral validation are distinct:

- **Installation validation:** Doctor confirms host detection, path resolution, eight folders, manifests, ownership, and hashes.
- **Behavioral validation:** A human reviews fresh-session traces for correct skill selection and behavior. It is not a deterministic filesystem assertion.

Each fixture must have a deliberate expected answer and known commands. Test negative cases too: a trivial local edit should not trigger broad architecture research, and an existing project design system should not trigger unrelated visual reinvention.

## 15. Security considerations

- A globally installed skill is executable guidance. Review Git updates before installing; do not auto-pull and do not trust a changed checkout merely because its path is familiar.
- v0.2 remains instruction-only. Future installers must not execute scripts found inside skill folders as part of validation.
- The installer must not overwrite host configuration or foreign skills, and must record ownership before it can delete anything.
- Validate source relative paths: reject rooted paths, `..` traversal, reparse-point escapes, unexpected directory entries, and duplicate/case-insensitive destination collisions.
- Verify copy hashes after staging and before final replacement. Treat source or destination changes during install as a failed transaction.
- Avoid Administrator elevation. If a proposed host location is not writable, report it; never silently elevate or install machine-wide.
- A plugin is not inherently safer: Claude documents that a plugin can run with user privileges. Plugin packaging therefore needs a separate trust review.

## 16. Windows and Unicode considerations

- Accept paths containing spaces and non-ASCII characters, including Korean user-profile names. Do not construct shell command strings from paths.
- Future PowerShell should use `-LiteralPath`, typed path APIs, and UTF-8 state files; it should avoid `cmd /c`, wildcard deletion, and lossy ANSI utilities.
- Normalize only for comparison, preserving the original display path. Compare canonical paths before every write/delete and ensure destinations stay under the resolved host skill root.
- Treat WSL and native Windows as separate environments. A Windows install does not imply that a WSL host sees the same home directory; doctor must report the actual environment rather than bridge it implicitly.
- Symlink and junction behavior is not a fallback path for copy mode. A stale reparse point at an expected destination is a failure requiring user review.

## 17. Failure and rollback strategy

Per host, installation is transactional as far as the filesystem permits: preflight, stage under the destination's parent, validate, replace only an owned matching target, then atomically update state where possible. A first install failure removes only the staged or newly created owned path. An update failure preserves the earlier verified owned copy and state.

Rollback is explicit: return the source checkout to the prior reviewed commit and rerun the installer. If files have been modified after install, uninstaller and rollback preserve them rather than guessing which content is safe to delete. Doctor reports the exact mismatch and the manual recovery path.

## 18. Deferred work

- Implementation of scripts, adapters, state schema, tests, and release/versioning.
- A portable cross-host plugin/package and marketplace metadata.
- Optional symlink mode, only with a separate Windows permission, stale-link, and trust review.
- Automated behavioral evaluation; model choice is probabilistic and needs fixtures plus human review.
- Distribution to WSL, enterprise-managed directories, other agents, and non-Windows platforms.
- Any change to the v0.1 skills or project instruction contract beyond packaging necessities proven during implementation.

## 19. Implementation plan for the next PR

1. Reconfirm current official docs and resolve the installable artifact boundary: each installed skill must retain access to every required reference/template without exposing the checkout.
2. Add a small PowerShell module plus `install.ps1`, `uninstall.ps1`, and `doctor.ps1`; no third-party dependencies.
3. Implement path resolution, source validation, collision detection, ownership state, copy staging, hash verification, and dry-run/apply semantics before host writes.
4. Implement Codex and Claude direct user-skill installation independently, with tests using Unicode and spaced temporary paths.
5. Add fixture-based installation tests and a documented manual fresh-session behavioral smoke-test protocol.
6. Run doctor against absent, clean, stale, collision, modified, partial-install, and rollback cases; add explicit documentation for every status.
7. Keep plugin packaging out of that PR unless official cross-host behavior is independently validated.
